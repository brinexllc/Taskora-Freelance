# PAY-01 / PAY-02 / PAY-03 — реализация и протокол

Дата: 2026-09-13. Исходный срез: `556ed75f5146d29b2a71e10dfa3cfe4a86ce41aa`.
Статус: реализованы локальные изменения и автоматические проверки. Допуск реальных денег не выдан: внешние проверки ниже не выполнены.

## Ручной вывод

Заявка проходит `pending → processing → paid`, `pending → cancelled/rejected`,
`processing → reconciliation_required`, а после подтверждённого отсутствия перевода — `processing → rejected`.
Из `reconciliation_required` доступны `paid/rejected` с подтверждением и основанием сверки.
Перевод в банке приложение не инициирует. Истечение сессии/потеря ответа не открывает заявку для нового перевода.

1. Пользователь подтверждает контакт, заданный `FINANCIAL_CONTACT_CHANNEL` (по умолчанию телефон).
2. Оператор через защищённый кабинет провайдера проверяет соответствие получателя владельцу аккаунта.
   В Taskora сохраняются непрозрачный токен получателя и ссылка на подтверждение проверки; полный номер карты не вводится.
   Маска карты служит подписью в интерфейсе и не считается подтверждением личности.
3. В админке «Payout recipients» оператор создаёт проверенного получателя. Нужны защищённая сессия,
   включённая MFA, недавнее повторное подтверждение и право `marketplace.operate_withdrawal`.
4. Пользователь выбирает получателя, сумму и подтверждает заявку. `POST /api/wallet/withdraw/` принимает
   `{amount, recipient, confirmed: true, idempotency_key}`. При потере ответа отправляется тот же запрос с прежним UUID.
   Одна транзакция создаёт заявку, один дебет с защищённой связью и уменьшает доступный баланс.
5. Оператор открывает конкретную заявку в админке и выбирает «Принять до внешнего перевода».
   После подтверждённого ответа `processing` зафиксированы оператор, время, сумма и проверенный получатель.
   Только после этого оператор выполняет внешний перевод по сохранённому снимку в защищённой системе провайдера.
6. «Подтвердить выполненный перевод» требует идентификатор банковской операции и ссылку на её подтверждение.
   Один идентификатор не может использоваться повторно в пределах провайдера и счёта.
7. Неизвестный исход переводится в `reconciliation_required`; деньги остаются зарезервированы. Для отказа после
   начала обработки обязательны подтверждение отсутствия перевода, основание и отдельный флаг `external_not_sent`.
8. Другой оператор может завершить заявку только с `marketplace.override_withdrawal` и объяснением причины.
   Применяется тот же контроль MFA и повторного подтверждения; override записывается в AuditLog.

Пользователь отменяет только `pending`. Повтор отмены `cancelled` безопасен. Для `processing`/сверки возвращается HTTP 409,
возврата нет. Дебет и возврат уникальны на уровне БД по `(withdrawal, withdrawal_event)`.
Принятый снимок и данные проверенного получателя неизменяемы через модель и интерфейсы приложения.
Прямой доступ администратора БД остаётся внешней границей доверия и требует ограниченных ролей.

Операторский API: `POST /api/operator/payout-recipients/verify/` принимает `user,provider,account,provider_recipient_id,destination,evidence`.
`GET/POST /api/operator/withdrawals/<id>/` требует те же полномочия, что админка; POST принимает
`action, idempotency_key, provider_reference, evidence, reason, external_not_sent`.
Пользовательский wallet не раскрывает provider recipient token, внутренний счёт и документы проверки.

## Миграции и исторические записи

Общая схема миграций добавляет nullable-связи и новые поля без изменения сумм. Отдельная инвентаризация
переводит существующие `pending` без снимка в `reconciliation_required`: старый перевод мог уже начаться.
Существующие `paid/rejected`, остатки, договоры и проводки сохраняются.

Перед выпуском оператор останавливает начало новых внешних переводов и сверяет каждую активную историческую заявку.
`backfill_withdrawal_ledger` по умолчанию выдаёт read-only JSON с кандидатами. Совпадение текста описания не считается
разрешением переноса: дополнительно проверяются пользователь, сумма, знак, тип, отсутствие связи с договором/платежом и время.
Неоднозначные кандидаты остаются в отчёте.

После независимой сверки уполномоченный администратор инфраструктуры может выполнить команду с `--apply-manifest reviewed.json`.
Формат: `[{"withdrawal": 123, "entry": 456, "event": "debit", "evidence": "approved-archive-reference"}]`.
Это явный перенос проверенных метаданных; команда блокирует строки, повторно проверяет единственность, записывает AuditLog
и не изменяет баланс, сумму, описание или дату. При неоднозначности вся транзакция откатывается.
Повтор того же manifest безопасен. Самостоятельное исправление денег командой отсутствует.

Для исторической заявки после привязки исходного дебета доступно действие `inventory` с правом override,
`recipient` (ID проверенного получателя), `evidence`, `reason` и UUID операции. Оно формирует подтверждённый снимок,
оставляет `reconciliation_required` и не разрешает новый перевод. Дальше оператор подтверждает ранее выполненный перевод
либо доказанный отказ с возвратом. Без подтверждённого исходного дебета возврат блокируется.

Откат выполняется восстановлением совместимой версии приложения/резервной копии по протоколу выпуска. Старый код,
который допускает отмену во время внешнего перевода, запрещено возвращать в обслуживание денежных операций.
Новые состояния нельзя автоматически обратно превращать в `pending`.

## Read-only финансовая сверка

`python manage.py reconcile_finances --provider-export normalized.csv --fail-on-incident` формирует JSON.
На PostgreSQL используется одна транзакция `REPEATABLE READ, READ ONLY`; команда не меняет БД.
Каждое расхождение — отдельный инцидент с кодом и идентификатором объекта. `--fail-on-incident` даёт ненулевой exit code,
чтобы оператор/контроль выпуска сохранил отчёт и расследовал отклонение.

Контроли: доступный баланс = подтверждённый начальный остаток + сумма всех проводок;
для закрытого резерва `gross + refund = amount`, фактический ledger net + fee = gross;
соответствие hold/refund/release/fee и единственного PlatformFee, зачислений/отмен Payment и проводок;
дебет/возврат Withdrawal и подтверждение внешней выплаты. Начальный остаток не выводится обратным расчётом из текущего баланса.
Для исторических и импортированных аккаунтов его подтверждает уполномоченный оператор в защищённой форме Wallet opening balance с независимым документом.
Без него отчёт содержит `opening_balance_unconfirmed`. При новой регистрации backend атомарно записывает известный нулевой
начальный остаток `source=registration`, `confirmed_by=null` и системное событие `wallet_opened` до любых проводок.
Операция проверяет отсутствие старого остатка и проводок, не применяется автоматически к существующим аккаунтам и не выдаётся за банковское подтверждение.

Нормализованный CSV содержит полный набор подтверждённых денежных операций за историю проверяемой базы:
`kind,reference,provider,account,amount,currency,status,external_reference`.
`kind`: `topup`, `cancellation`, `withdrawal`; суммы положительные в UZS с точностью 0.01;
`reference`: UUID Payment/Withdrawal; `external_reference`: фактический ID провайдера; `status`: `confirmed`.
Для withdrawal обязательна согласованность счёта провайдера; для пополнений account сохраняется в выгрузке, но
старые Payment не содержат снимка merchant account, поэтому автоматическая проверка его идентичности ограничена.
Оператор дополнительно проверяет происхождение и полноту экспорта. Разные topup/refund одной PAYME-транзакции имеют разные `kind`.
Дубликаты, неизвестные, пропавшие операции, неверные суммы/валюты/статусы или чужие внешние ID создают инциденты.
Без CSV отчёт явно пишет `provider_export: not_supplied`, `ok: false`; внутреннее равенство не выдаётся за сверку банка.

## Автоматические проверки

Добавлены сценарии: контакты и получатель; полный PAN запрещён; повтор создания/финализации/отмены;
чужой ключ; второй оператор; истекшее повторное подтверждение; конфликт cancel/processing; неизвестный исход;
однократный возврат; повторное использование банковского подтверждения; immutable snapshot;
историческая инвентаризация; уникальность БД; чужой кошелёк; read-only обнаружение расхождения;
явный исторический manifest и отказ при неоднозначности.

PostgreSQL-набор содержит параллельные claim/claim, claim/cancel, создание/создание, paid/paid,
CLICK complete/complete и PAYME perform/perform. Существующие CLICK/PAYME тесты сохранены:
неверная подпись/сумма/чужой ID, отмена уже потраченных средств, задержка/повтор callback, отсутствие зачисления
по redirect, fiscal worker timeout/restart, отложенный чек, потеря worker lease, отсутствие второго fiscal POST.

Результаты конкретных запусков записываются в общем протоколе выпуска и в `.taskora-qa/audit-postgresql/tests-*.log`.
Изолированный PostgreSQL запуск `test_withdrawals test_admin_operations test_payme test_click`: **47 тестов успешно**, 21.113 с,
без пропусков. Лог: `tests-marketplace_test_withdrawals-marketplace_test_admin_operations-marketplace_test_payme-marketplace_te.log`.
Локальный SQLite запуск 44 тестов: успешно, 3 PostgreSQL concurrency tests штатно пропущены;
он выполнен до добавления дополнительных PG callback/inventory тестов и не заменяет PostgreSQL-протокол.

## Внешние проверки PAY-03 — не выполнены

Доступ в sandbox CLICK/PAYME, реальные банковские выгрузки, выдача фискального чека тестовой кассой,
проверка привязки merchant account, контролируемые callbacks с кабинетов провайдеров и перезапуск deployed worker
не выполнялись. Все provider IDs в тестах синтетические; сетевые ответы fiscal unit tests — mock.
Наличие ключей или `integrations.click/payme=true` не подтверждает испытания провайдера.

Для допуска владелец/провайдер сохраняет отдельный sandbox-протокол без секретов: deployed SHA, среда,
время, provider transaction ID, внутренний UUID, положительный/отрицательный callback, повтор, задержка,
отмена до/после использования средств, fiscal success/error/delay, worker restart, итог ledger, ссылка на чек,
подпись проверившего. Невыполненный сценарий помечается явно. Рабочая касса и контрольная реальная операция —
отдельный согласованный шаг владельца и провайдера. До этого production `REAL_MONEY_ENABLED=false` блокирует создание
новых checkout/выводов, сохраняя обработку уже пришедших подписанных callbacks для ранее созданных платежей.

Самого включения `REAL_MONEY_ENABLED=true` в staging/production недостаточно. `LEGAL_CONTENT_PATH` должен указывать
на утверждённый владельцем и юристом manifest с `approved: true`, `operator` с непустыми строками
`legal_name,tax_id,address` и `support` со строками `email,response_time,withdrawal_rules,refund_rules,dispute_rules`.
Email проходит проверку формата. Значения не подставляются автоматически: владелец предоставляет реальные реквизиты,
контакт, сроки и правила, а служба поддержки подтверждает работоспособность канала отдельным внешним испытанием.
Проверка конфигурации не подтверждает юридическую действительность документов и не заменяет протокол допуска.
