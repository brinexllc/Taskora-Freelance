## Состояния готовности

«Реализовано» означает наличие кода и миграций. «Проверено локально» означает фактический запуск указанного теста на изолированной базе. «Включено в production» требует подтверждения владельца и отдельного протокола. Изменения кода не являются банковской сертификацией, юридическим согласованием, сменой инфраструктурного секрета или проверкой живого Figma.

Сохраняются 5% с исполнителя / 0% с заказчика, снимки старых тарифов, существующие балансы и связи, 8 направлений и 89 базовых навыков, четыре языка и две темы. Возрастные ограничения не меняются. P2 из аудита — отдельные гипотезы развития, а не неявное внедрение цифровых товаров, автоматических выплат или ONEID.

## SEC-01: отдельный протокол владельца

1. Зафиксировать время инцидента; отозвать опубликованный пароль в панели PostgreSQL и обновить зависимые переменные backend, workers и migration job. Значения вводятся только в защищённый менеджер секретов.
2. Подготовленный `ops/runtime-role.sql` адаптировать к действительному имени БД и migration owner. Runtime-роль не должна быть владельцем схемы или суперпользователем. Миграции запускает отдельная роль.
3. Проверить, что старые реквизиты больше не создают соединение. Проверить все workers с новым доступом. При необходимости владелец завершает старые соединения по отдельно проверенному списку.
4. Проверить журналы входов, DDL и изменение данных за период раскрытия, сверить суммы. При посторонней активности — расследование и отзыв сессий. Не запускать SQL для «исправления» денег.
5. В протокол внести время, исполнителя, успешный отзыв старого доступа, SHA сервисов, результат сверки и идентификатор инцидента. Не записывать пароль или connection string.

Фактическая ротация и проверка журналов production данным выпуском не выполняются: их исполнитель по ТЗ — владелец инфраструктуры.

## Изолированный local/test

Нужны Python 3.14, Node.js 22.13+, pnpm. `start-local.ps1 backend` использует отдельную SQLite, явный `TASKORA_ENV=local`, отключает загрузку общей `.env`; `start-local.ps1 frontend` задаёт локальный upstream. На чистом окружении установите `requirements.txt` и `pnpm install --frozen-lockfile`.

```powershell
$env:TASKORA_ENV = 'test'
$env:TASKORA_LOAD_DOTENV = 'false'
$env:DJANGO_DEBUG = 'true'
.venv/Scripts/python.exe backend/manage.py test marketplace --noinput
.venv/Scripts/python.exe scripts/run_isolated_postgres_tests.py
```

PostgreSQL runner использует только loopback `127.0.0.1:55442`, отдельную БД и локальный каталог `.taskora-qa/audit-postgresql`. Путь к установленным бинарникам можно задать `TASKORA_PG_BIN`. Секрет тестовой БД создаётся локально и не выводится. Тесты Django не читают production `DATABASE_URL`. Не подставляйте production URL в `TEST_DATABASE_URL`.

Браузер работает через `/api` на origin frontend. Server proxy обращается к `API_URL`; cookie авторизации HttpOnly, CSRF выдается отдельным endpoint и передается заголовком. Proxy должен передавать Origin/Referer и не кэшировать персональные ответы. Для административного интерфейса нужен тот же origin/path routing к `/admin` и серверным static, чтобы использовать проверенную browser session. Вход только паролем в Django Admin не обходит MFA.

## OPS-01: обязательные переменные

`TASKORA_ENV`: local/test/staging/production. Для staging/production: `DJANGO_DEBUG=false`, отдельный `DJANGO_SECRET_KEY` не короче 50 символов, PostgreSQL `DATABASE_URL`, точные `DJANGO_ALLOWED_HOSTS`, HTTPS `FRONTEND_URL`/`PUBLIC_API_URL`, точные `CSRF_TRUSTED_ORIGINS`/`CORS_ALLOWED_ORIGINS`, постоянный `PRIVATE_MEDIA_ROOT`, отдельный Fernet `SECURITY_MFA_ENCRYPTION_KEY`. Запрещены wildcard, localhost и некорректные bool. MFA encryption key также резервируется защищённо; его потеря делает существующие TOTP секреты нечитаемыми.

Frontend: явный `TASKORA_ENV`, обязательный HTTPS `NEXT_PUBLIC_API_URL` для production build/start, серверный `API_URL`. Публичный URL не должен содержать секреты. Runtime повторно проверяет конфигурацию. Local/test допускают HTTP loopback.

`REAL_MONEY_ENABLED=false` по умолчанию. Одного переключения недостаточно: legal manifest должен иметь `approved:true` и реальные operator/support поля по схеме из `docs/payments-audit.md`. Переключение после внешней приёмки — отдельный шаг владельца. `PAYME_TEST_MODE=true` несовместим с реальными деньгами. Провайдер без полного набора реквизитов недоступен. Входящие подтверждённые callbacks существующих платежей продолжают обрабатываться независимо от остановки новых операций.

## Миграции и порядок выпуска

1. Остановить создание/claim новых выводов; инвентаризировать уже начатые внешние переводы, остановить старые app instances/операторские формы. Снять согласованные backup БД и приватных файлов.
2. Применить добавочные миграции отдельным migration job до запуска нового кода. `0015` добавляет модели/nullable evidence и ограничения, `0016` переводит исторические pending в `reconciliation_required`, `0017` добавляет снимки подтверждённых контактов, `0018` — ограниченные API-токены и источник начального остатка. Новые profile proof fields остаются пустыми у прежних пользователей. Только для новой регистрации фиксируется известный нулевой начальный остаток; исторические суммы не выводятся из текущего баланса.
3. Исторические paid/rejected, связи, балансы и тарифы не пересчитываются. Даты сдачи старых договоров не угадываются. Старые неоднозначные записи кошелька выдаются отчётом; backfill выполняется только по проверенному manifest, без изменения сумм.
4. Выпустить согласованную версию backend/frontend, проверить маршруты с cookie/CSRF и отключение бессрочных legacy tokens. При необходимости временного legacy окна задать конкретную конечную дату `SECURITY_LEGACY_TOKEN_UNTIL` и ограниченный возраст токена; после перехода отозвать записи Token штатной командой.
5. Запустить workers, проверки и сверку. Выдать операторам только необходимые permissions, включить TOTP и повторное подтверждение действия. Для прежних незавершённых выводов заполнить инвентаризацию и доказательства; не запускать перевод повторно при неизвестном результате.
6. Проверить `manage.py makemigrations --check --dry-run`, `/api/health/`, `/api/health/ready/`, read-only `reconcile_finances`, `release_passport --frontend-sha <SHA>`. У health и readiness разные назначения: ни один не подтверждает работу банка.

Откат — согласованный откат кода с сохранением новой схемы и запретом финансовых mutations старым кодом. Не выполнять reverse `0015` с накопленными evidence: это удалит новые таблицы. `0016` необратимо сохраняет безопасное состояние при откате данных. Перед каждым вариантом отката прогнать его на восстановленной копии. Включать старые browser tokens для «быстрого исправления» запрещено.

## OPS-02: workers, наблюдение, backup и restore

Обязательный worker при CLICK: `process_click_receipts --watch`. Worker `process_operations --watch` прописан в Procfile/compose: раз в минуту запускает `escalate_reviews`, проверяет очереди, схему и HTTP readiness; уведомление о сроке проверки не двигает деньги. С опцией `--notify` и HTTPS `OPERATIONS_ALERT_WEBHOOK` он отправляет инцидент/восстановление только при изменении состояния. Сам webhook и доставку подтверждает владелец. Одноразовая проверка — `check_operations`, ненулевой exit означает инцидент. За остановкой сразу API и workers должен следить независимый внешний монитор `/api/health/ready/`: внутри полностью выключенной инфраструктуры уведомление невозможно.

Владелец согласует RPO/RTO, периодичность, срок хранения, шифрование и offsite-хранилище резервных копий. До согласования численные обещания не задаются. Согласованный snapshot включает PostgreSQL, все объекты PRIVATE_MEDIA_ROOT и защищённую резервную копию ключа MFA. Для согласованности при файловом backup остановить загрузки и обработчики, либо использовать синхронизированные snapshots.

Restore выполняется исключительно в новую изолированную БД/том: восстановить dump и файлы, проверить миграции, хеши файлов и `reconcile_finances`, затем проверить скачивание участником и отказ постороннему. Сравнить SHA приложения, migrations и денежные контрольные суммы до/после. `scripts/check_isolated_restore.py` демонстрирует эту процедуру на искусственной БД; production backup/redeploy он не подтверждает. Измеренные длительности фиксируются в verification report отдельно от утверждённых RPO/RTO.

## API и продукт

Новые маршруты и проверки выплат: `docs/payments-audit.md`. Контакты, сессии, MFA, атомарные лимиты и legal manifest: `docs/security-audit.md`.

- `POST projects/{id}/clone/`: только владелец отменённого до резерва заказа, UUID `idempotency_key`, новый deadline, повторная валидация. Возвращает draft с `source_project`. Вложения только с `copy_attachments=true` и подтверждением прав; деньги/отклики/договор не копируются.
- `GET/POST proposals/{id}/conversation/`, `GET proposal-conversations/`, `GET/POST .../{id}/messages/`, `POST .../{id}/read/` с `through_id`, `POST .../{id}/report/` с основанием, защищённое скачивание. Диалог остаётся связан с исходным proposal после договора. Посторонние и staff без отдельного аудированного основания доступа не получают.
- Project/Contract: `acceptance_criteria`, `demonstration_method`, `test_scenario`, `review_days`. Новые договоры требуют заполнения до подписи. `POST contracts/{id}/amend/` требует `expected_version`; до резерва сбрасывает подписи, после резерва создаёт предложение. Второй участник подтверждает `.../amendments/{id}/accept/`.
- `submit`: файл, preview, `verification_steps`, необязательный HTTPS `demo_url`; сохраняются версия условий, deadline_snapshot, срок проверки. Ссылка не запускается и не проксируется backend. Секреты демо передавать только участникам; само внешнее staging приложение также должно ограничивать доступ.
- `accept`: явно подтверждённая выплата и `deliverable_id` проверенной версии. Принятая сдача фиксируется. Истечение срока проверки никогда не выплачивает автоматически. Исходники сохраняют прежнюю защиту.
- «Вовремя»: дата принятой сдачи против сохранённого deadline. Споры и отсутствие доказуемой даты исключены; неизвестное не превращается в 100%. Каталог использует агрегаты и prefetch, без base64-портфолио в списке; полный профиль сохраняется.

## GOV-01 и внешняя приёмка

Legal manifest содержит конкретную версию, hash, язык и snapshot согласия. Поставляемые тексты имеют статус `approved:false`. Владелец и местный юрист должны подтвердить фактическое юрлицо/реквизиты, поддержку, сроки спора/возврата/вывода, персональные данные, правила для 16–17 лет и схему денег. Реальный канал поддержки проверяется отдельным обращением владельца. Технический резерв не называется банковским эскроу; подтверждение в аккаунте не называется E-IMZO/ONEID.

PAY-03: кабинеты CLICK/PAYME, fiscal sandbox, restart worker с провайдером и контрольные реальные операции имеют отдельный протокол с тестовыми transaction IDs и результатами, без секретов. Наличие адаптеров/ключей не заменяет этих проверок. Живой Figma, Railway deployed SHA, права/персистентность реального тома и работоспособность SMTP/SMS также требуют отдельного фактического подтверждения.
