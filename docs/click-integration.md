# Подключение CLICK к Taskora

Интеграция пополняет кошелёк через платёжную страницу CLICK и Shop API Prepare/Complete. При включённой фискализации отдельный процесс передаёт согласованную позицию услуги через Merchant API, получает ссылку на чек и показывает её владельцу платежа. Резервирование по договору, приёмка и выплата исполнителю остаются отдельными операциями.

Источники, проверенные 8 сентября 2026 года: [платёжная ссылка](https://docs.click.uz/click-button/), [Shop API](https://docs.click.uz/shop-api/requests), [Merchant API](https://docs.click.uz/merchant-api/requests), [фискализация](https://docs.click.uz/merchant-api/fiscalization). Сайт документации отдаёт начальную HTML-страницу для вложенных URL; содержание разделов проверено в загружаемых им JavaScript-модулях.

## Реквизиты и схема чека

Заполните серверные переменные из `.env.example`. Ключи не передаются браузеру и не включаются в репозиторий.

| Переменная | Значение |
| --- | --- |
| `CLICK_SERVICE_ID` | ID сервиса от CLICK |
| `CLICK_MERCHANT_ID` | ID мерчанта от CLICK |
| `CLICK_SECRET_KEY` | Secret Key от CLICK |
| `CLICK_MERCHANT_USER_ID` | Пользователь мерчанта для заголовка Auth Merchant API |
| `CLICK_FISCALIZATION_ENABLED` | По умолчанию `true`; новые платежи недоступны при неполной настройке чеков |
| `CLICK_FISCAL_ITEM_NAME` | Согласованное название услуги с единицей измерения, до 63 символов |
| `CLICK_FISCAL_SPIC` | Согласованный 17-значный ИКПУ |
| `CLICK_FISCAL_PACKAGE_CODE` | Код упаковки, до 20 цифр |
| `CLICK_FISCAL_VAT_PERCENT` | Целая ставка НДС; `0` указывается явно |
| `CLICK_FISCAL_TIN` / `CLICK_FISCAL_PINFL` | Ровно один реквизит для CommissionInfo: ИНН из 9 цифр или ПИНФЛ из 14 |
| `FRONTEND_URL` | Публичный HTTPS-адрес фронтенда |

Реализован вариант одного согласованного наименования для полной суммы пополнения, количество 1, оплата картой, НДС включён в сумму. Название, ИКПУ, упаковку, ставку, реквизиты CommissionInfo и применимость такого чека к пополнению кошелька должен подтвердить CLICK/ответственный за фискальную схему. Значения намеренно не подставлены. Это не чек комиссии при приёмке работы и не распределение товаров разных исполнителей. Если требуется такая схема, её следует согласовать и описать отдельно до приёма денег.

Параметр `CLICK_FISCALIZATION_ENABLED=false` предназначен для согласованного с CLICK случая, когда чеки формируются отдельно. Он не включает имитацию оплаты. Обработчик Complete продолжает принимать ранее подготовленные платежи при недоступности фискальной конфигурации; зачисление подтверждённой оплаты не зависит от ответа OFD.

## Настройка в CLICK

Укажите два публичных HTTPS-адреса backend (со завершающим `/`):

- Prepare: `https://<api-domain>/api/payments/click/prepare/`
- Complete: `https://<api-domain>/api/payments/click/complete/`

`transaction_param` / `merchant_trans_id` — UUID платежа Taskora. Формат поля заказа должен принимать строку UUID. Сумма Shop API передаётся в сумах с двумя знаками после точки. CLICK отправляет `application/x-www-form-urlencoded`; ответ — JSON с кодом протокола. Callback не использует пользовательский токен или CSRF-cookie.

Проверяются MD5-подпись из исходных строк запроса, service_id, сумма, click_trans_id, click_paydoc_id, merchant_prepare_id и переходы статусов. Повторный Complete возвращает `-4`, отменённый платёж — `-9`. Кошелёк зачисляется только один раз в транзакции с записью в журнале движений. Переход по return_url не зачисляет деньги.

## Запуск

Примените миграцию `0008_clickfiscalreceipt` к нужной базе вместе с выпуском backend. Старые платежи она не изменяет и не фискализирует задним числом.

```powershell
# Локальные проверки должны использовать локальную БД, а не DATABASE_URL production из .env.
$env:DATABASE_URL = 'sqlite:///' + (Join-Path (Get-Location) 'backend/local-mvp.sqlite3').Replace('\', '/')
$env:DJANGO_DEBUG = 'true'
.\.venv-mvp\Scripts\python.exe backend/manage.py migrate --noinput
.\.venv-mvp\Scripts\python.exe backend/manage.py process_click_receipts --check-config
```

После заполнения реквизитов запустите третий локальный процесс:

```powershell
.\start-local.ps1 click-receipts
```

Production: отдельный worker из того же образа и с той же БД/переменными среды, команда `python backend/manage.py process_click_receipts --watch`. Для платформ с Procfile добавлен процесс `click_receipts`; его нужно включить при развёртывании. Однократная обработка очереди: `python backend/manage.py process_click_receipts --limit 100`. Docker Compose: `docker compose --profile click up --build` после заполнения `.env`. Обычный backend не отправляет чеки самостоятельно.

Worker разрешает Merchant API payment_id через `payment/status_by_mti` по service_id, UUID и дате из подписанного Complete, проверяя возвращённый UUID. Идентификаторы Shop API не подставляются вместо Merchant API payment_id. Затем он вызывает `payment/ofd_data/submit_items` и получает `payment/ofd_data/<service_id>/<payment_id>`. Все суммы чека — целые тийины, НДС округляется до тийина. Заголовок `Auth` формируется как `merchant_user_id:sha1(timestamp + secret_key):timestamp`. HTTPS-переадресации запрещены; сетевой таймаут — 10 секунд.

## Контроль и сбои

В Admin → Click fiscal receipts видны состояние, число попыток и краткая ошибка без секретов. Настройки позиции копируются при checkout: изменение `.env` не меняет чек уже созданного платежа. Очередь находится в БД и переживает перезапуск. Обрабатываются только оплаченные платежи. Несколько worker-процессов разделяют задания через блокировку записи и аренду на 5 минут; после падения аренда истекает.

До POST сохраняется состояние `submitting`. При таймауте, ошибке или перезапуске повторный POST автоматически не выполняется: документация не гарантирует его идемпотентность. Worker проверяет наличие чека через GET. Подтверждённая отправка без готового QR остаётся в `submitted`. Ошибки поиска платежа до POST можно повторять. Между попытками действует возрастающая задержка, максимум 1 час. После 10 попыток состояние становится `review`.

Для `review` сверьте платёж и наличие чека в CLICK, используя сохранённый Merchant API payment_id и UUID Taskora. Не удаляйте запись и не отправляйте новый чек до сверки результата первой отправки. Автоматическая повторная выдача после неопределённого результата не предусмотрена. Если Complete пришёл по старому подготовленному платежу без фискальных настроек, запись `review` с пустым снимком требует отдельного решения ответственного за чеки.

Кошелёк показывает ссылку только на HTTPS-чек `ofd.soliq.uz`. API статуса `/api/payments/<uuid>/` доступен только владельцу; фискальные реквизиты и внутренние ошибки туда не включаются. После возврата с оплаты интерфейс проверяет статус до двух минут, после чего пользователь может обновить кошелёк.

## Приёмочная проверка с CLICK

После выдачи ключей и активации сервиса проверьте в согласованной среде CLICK: переход на оплату, Prepare, успешный Complete, один прирост баланса, получение чека с правильной суммой/НДС, отмену и повтор Complete. Автотесты используют только синтетические реквизиты и подменённые ответы; они не подтверждают доступность реального мерчанта или банковскую сертификацию. Вывод денег на карту и возврат списанного платежа через Merchant API в эту интеграцию пополнения не входят.
